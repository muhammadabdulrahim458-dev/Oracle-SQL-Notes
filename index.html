Section 1: Introduction to Database Systems (CLO1 – Understanding)

1.1 Basic Concepts

What is a Database?

A database is an organized collection of related data.
Example: Your phone's contact list – names, phone numbers, emails – stored in a structured way.

What is a DBMS?

A DBMS (Database Management System) is software that helps you create, manage, and interact with databases.
Examples: Oracle, MySQL, Microsoft SQL Server, PostgreSQL.

Real-life analogy:
A database is like a filing cabinet full of folders (data). The DBMS is like a clerk who knows where everything is, can search quickly, add new folders, remove old ones, and give you only the information you ask for.

Database System

A complete database system = Database + DBMS + Applications + Users.

File System vs. DBMS (Advantages of Databases)

File System (e.g., Excel files, text files) DBMS
Data is scattered across many files All data is centralized
Duplicate data possible (e.g., same customer name in three files) Avoids duplication through controlled sharing
No security – anyone can open the file User authentication and privileges
Hard to query: "Find all customers who bought product X" would require manual search or custom code Easy query with SQL: SELECT * FROM Customers WHERE product = 'X';
Concurrent access can corrupt files (two people editing same file) Handles concurrency automatically

Data Abstraction (Three Levels)

To simplify how users see data, DBMS uses three levels:

  1. External Level (View level) – What individual users see (e.g., a student only sees his grades, not all students).
  2. Conceptual Level (Logical level) – What data is stored and how it relates (e.g., "Students have IDs, names, and a list of courses").
  3. Internal Level (Physical level) – How data is actually stored on disk (bits, bytes, indexes). Users never see this.

Real-life example:
When you use a banking app:

  • External: You see your balance and recent transactions.
  • Conceptual: The bank knows each account has an account number, owner, balance, and a list of transactions.
  • Internal: The data is stored on hard drives, maybe encrypted, with indexes to find your account quickly.

Data Independence

  • Logical Data Independence: You can change the conceptual schema (e.g., add a new column "middle name") without changing external views or applications.
  • Physical Data Independence: You can change the internal storage (e.g., use a different indexing method) without changing the conceptual or external schemas.

1.2 Database Environment

Components of a Database Environment

A typical database environment includes:

[Users] → [Applications] → [DBMS] → [Database] → [Stored Data]
         ↑                               ↑
    [Query Tools]                  [Backup/Recovery]

Detailed components:

  1. Hardware – The computer(s) running the DBMS (servers, storage disks).
  2. Software – The DBMS software itself (Oracle, MySQL, etc.), plus operating system, network software.
  3. Data – The actual stored data (the most important component).
  4. Procedures – Rules for using the system (backup procedures, security rules).
  5. People – Database administrators (DBAs), developers, end-users.

Real-life example – University registration system:

  • Hardware: University servers.
  • Software: Oracle DBMS.
  • Data: Student records, course lists, enrollments.
  • Procedures: "Every night at 2 AM, backup the database."
  • People: IT staff, professors (enter grades), students (register).

Different Categories of Databases

Based on how data is organized:

  1. Relational Databases (RDBMS) – Data in tables with rows and columns. Uses SQL. Examples: Oracle, MySQL, PostgreSQL. (This is our focus.)
  2. NoSQL Databases – For unstructured or semi-structured data, high scalability. Types:
    • Document stores (MongoDB)
    • Key-value stores (Redis)
    • Column-family (Cassandra)
    • Graph databases (Neo4j)
  3. Object-Oriented Databases – Stores objects (like in Java/C++). Less common.
  4. Hierarchical / Network Databases – Older models (like IBM IMS).

When to use which?

  • Use relational for most business apps (banking, university, e-commerce).
  • Use NoSQL for social media feeds, real-time analytics, huge web-scale data.

Enterprise Applications and ERP Systems

  • Enterprise Applications are large software systems used by organizations. They rely heavily on databases.
  • ERP (Enterprise Resource Planning) – An integrated system that manages all business processes: finance, HR, inventory, sales, etc. All modules share one central database.

Example: SAP, Oracle ERP. When you order a product, the ERP's database updates inventory, creates an invoice, and schedules shipping – all from the same data.

Data Warehouse

  • A data warehouse is a large, centralized repository of data collected from different sources (operational databases, external data). It is optimized for analysis and reporting, not for day-to-day transactions.
  • Difference from regular database:
    Regular DB (OLTP – Online Transaction Processing) handles many small transactions (e.g., buying a coffee).
    Data warehouse (OLAP – Online Analytical Processing) handles large complex queries over years of data (e.g., "What were monthly sales trends for the last 5 years?").

Real-life example:
Walmart's daily sales happen in their operational databases. Every night, that data is copied into a data warehouse. Analysts then query the warehouse to decide which products to promote.

1.3 Database Lifecycle

Design Life Cycle of Databases

The database doesn't just appear; it goes through a planned lifecycle. The main phases: 

Requirements Analysis → Conceptual Design → Logical Design → Physical Design → Implementation → Maintenance

PlantUML Code for Database Lifecycle (Flowchart):

Detailed explanation of each phase:

  1. Requirements Analysis

    • Talk to users, understand what data they need, what queries they will run.
    • Output: A requirements document.

  2. Conceptual Design

    • Create a high-level description of data using the Entity-Relationship (ER) model.
    • Output: ER diagram (entities like Student, Course; relationships like Enrolls).

  3. Logical Design

    • Transform the ER model into tables (relations) – independent of any specific DBMS.
    • Apply normalization rules to avoid redundancy.
    • Output: Relational schema (e.g., Students(SID, Name, Major)).

  4. Physical Design

    • Choose storage structures, indexes, partitioning – specific to the chosen DBMS (e.g., Oracle).
    • Output: Physical design document.

  5. Implementation

    • Write SQL DDL (CREATE TABLE, etc.) to build the database.
    • Load data and set up user privileges.

  6. Maintenance & Tuning

    • Monitor performance, add/change indexes, handle backups, evolve schema as requirements change.

Real-life example – Building a library database:

  • Requirements: Librarians need to track books, members, loans.
  • Conceptual: Entities = Book, Member, Loan. Relationships = Member borrows Book.
  • Logical: Tables: Book(ISBN, title, author), Member(MemberID, name), Loan(LoanID, ISBN, MemberID, date).
  • Physical: Add index on Loan(date) for quick overdue searches.
  • Implementation: Run SQL commands in Oracle.
  • Maintenance: Add a new column "Genre" later.

Section 2: SQL (Oracle) – Data Definition & Manipulation Language (CLO4 – Applying)

Overview of SQL

SQL (Structured Query Language) is the standard language for relational databases. Oracle uses its own dialect, which is mostly standard but has some specific features.

Four main categories of SQL commands:

Category Purpose Commands
DDL (Data Definition Language) Define/change database structure CREATE, ALTER, DROP, TRUNCATE, RENAME
DML (Data Manipulation Language) Manage data inside tables INSERT, UPDATE, DELETE, MERGE
DQL (Data Query Language) Retrieve data SELECT
DCL (Data Control Language) Permissions GRANT, REVOKE
TCL (Transaction Control Language) Transactions COMMIT, ROLLBACK, SAVEPOINT

We'll cover DDL first, then DML, then DQL (queries) in detail.

2.1 Data Definition Language (DDL)

DDL commands create, modify, and remove database objects like tables, indexes, and schemas.

Creating a Table – CREATE TABLE

Syntax (simplified):

CREATE TABLE table_name (
    column_name1 datatype constraint,
    column_name2 datatype constraint,
    ...
    table_constraint
);

Real-life example: You are building a database for a university. You need a students table. 

CREATE TABLE students (
        student_id NUMBER (6) PRIMARY KEY,
        first_name VARCHAR2 (50) NOT NULL,
        last_name VARCHAR2 (50) NOT NULL,
        email VARCHAR2 (100) UNIQUE,
        enrollment_date DATE DEFAULT SYSDATE,
        major VARCHAR2 (50)
    );

What each part means:

  • student_id NUMBER(6) – Column holds numbers up to 6 digits.
  • PRIMARY KEY – Uniquely identifies each row, cannot be NULL.
  • VARCHAR2(50) – Variable-length text up to 50 characters. (Oracle's preferred string type.)
  • NOT NULL – This column must have a value.
  • UNIQUE – No two rows can have the same email.
  • DEFAULT SYSDATE – If you don't provide a date, Oracle uses the current date and time.
  • SYSDATE – Oracle function for current date/time.

Oracle Data Types (Most Common)

Data Type Description Example
NUMBER(p,s) Number with precision p total digits, s digits after decimal NUMBER(8,2) → 123456.78
VARCHAR2(n) Variable-length string, max n bytes/characters VARCHAR2(100) → 'John'
CHAR(n) Fixed-length string, padded with spaces CHAR(10) → 'John '
DATE Date and time (century, year, month, day, hour, minute, second) '05-MAY-2026'
TIMESTAMP DATE with fractional seconds '05-MAY-2026 14:30:00.123'
CLOB Large text (up to 4GB) For essays, documents
BLOB Binary data (images, files) Photo of student

Best practice: Use VARCHAR2 for almost all string columns. Use CHAR only for fixed-length codes like 'M'/'F' or state abbreviations.

Constraints (Rules for Data Integrity)

Constraints ensure data is accurate and reliable. They can be column-level (after column) or table-level (after all columns).

Constraint Description Example
PRIMARY KEY Unique + Not Null, only one per table student_id NUMBER PRIMARY KEY
FOREIGN KEY References a primary key in another table course_id NUMBER REFERENCES courses(course_id)
UNIQUE All values must be different (NULLs allowed) email VARCHAR2(100) UNIQUE
NOT NULL Cannot be empty first_name VARCHAR2(50) NOT NULL
CHECK Custom condition age NUMBER CHECK(age >= 18)

Example with all constraints (table-level syntax):

CREATE TABLE enrollments (
    student_id NUMBER(6),
    course_id  NUMBER(6),
    enroll_date DATE DEFAULT SYSDATE,
    grade      CHAR(2),
    -- Table-level constraints
    CONSTRAINT pk_enrollments PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_enroll_student FOREIGN KEY (student_id) REFERENCES students(student_id),
    CONSTRAINT fk_enroll_course FOREIGN KEY (course_id) REFERENCES courses(course_id),
    CONSTRAINT chk_grade CHECK (grade IN ('A','B','C','D','F'))
);

Altering a Table – ALTER TABLE

After creating a table, you can modify its structure.

Add a new column:

ALTER TABLE students ADD (phone VARCHAR2(15));

Modify column datatype or constraint:

ALTER TABLE students MODIFY (phone VARCHAR2(20) NOT NULL);

Rename a column:

ALTER TABLE students RENAME COLUMN phone TO mobile;

Drop a column:

ALTER TABLE students DROP COLUMN mobile;

Add a constraint:

ALTER TABLE students ADD CONSTRAINT chk_age CHECK (age >= 16);

Drop a constraint:

ALTER TABLE students DROP CONSTRAINT chk_age;

Real-life scenario: The university decides to store student's birthdate. You don't need to recreate the table – just ALTER it.

Dropping a Table – DROP TABLE

Removes the table and all its data permanently (unless you use a flashback feature). 

DROP TABLE students;

Safer version (prevents "orphan" foreign key references): 

DROP TABLE students CASCADE CONSTRAINTS;

Truncating a Table – TRUNCATE TABLE

Removes all rows quickly, but keeps the table structure for future use. Cannot be rolled back (in most cases). 

TRUNCATE TABLE students;

Difference between DELETE (DML) and TRUNCATE (DDL):

DELETE TRUNCATE
DML (can rollback) DDL (auto-commit, cannot rollback)
Slower on large tables Very fast
Can have WHERE condition Removes all rows unconditionally
Does not reset storage Deallocates storage

2.2 Data Manipulation Language (DML)

DML commands work with the data inside tables.

Inserting Rows – INSERT

Insert a single row (all columns):

INSERT INTO students (student_id, first_name, last_name, email, enrollment_date, major)
VALUES (101, 'Ali', 'Raza', 'ali.raza@university.edu', DATE '2025-09-01', 'CS');

Insert with default values (Oracle uses DEFAULT):

INSERT INTO students (student_id, first_name, last_name, email, major)
VALUES (102, 'Sara', 'Khan', 'sara.khan@university.edu', 'CS');
-- enrollment_date will be SYSDATE automatically

Insert without column list (not recommended – fragile): 

INSERT INTO students VALUES (103, 'Bilal', 'Ahmed', 'bilal@uni.edu', SYSDATE, 'EE');
-- Must provide values for EVERY column in the order defined.

Insert multiple rows (Oracle 23c+ or using UNION ALL): 

INSERT ALL
    INTO students VALUES (104, 'Ayesha', 'Malik', 'ayesha@uni.edu', SYSDATE, 'CS')
    INTO students VALUES (105, 'Omar', 'Hassan', 'omar@uni.edu', SYSDATE, 'CS')
SELECT * FROM dual;

Insert from another table (subquery):

INSERT INTO old_students (student_id, full_name)
SELECT student_id, first_name || ' ' || last_name FROM students WHERE enrollment_date < DATE '2020-01-01';

Updating Rows – UPDATE

Modify existing data.

UPDATE students 
SET major = 'Software Engineering' 
WHERE student_id = 101;

Update multiple columns:

UPDATE students 
SET major = 'AI', email = 'ali.new@university.edu' 
WHERE last_name = 'Raza';

Update all rows (be careful!):

UPDATE students SET enrollment_date = SYSDATE;  -- every student gets today's date

Deleting Rows – DELETE

Remove rows from a table.

DELETE FROM students WHERE student_id = 105;

Delete all rows (slow, but rollbackable):

DELETE FROM students;  -- table becomes empty, but structure remains

Delete based on another table:

DELETE FROM students 
WHERE student_id IN (SELECT student_id FROM old_students);

Important: Always test your DELETE and UPDATE with a SELECT first: 

SELECT * FROM students WHERE last_name = 'Raza';  -- see what will be affected
DELETE FROM students WHERE last_name = 'Raza';

Transaction Control (TCL) – Quick Introduction

When you run DML commands (INSERT, UPDATE, DELETE), changes are not permanent until you COMMIT. This allows you to undo mistakes with ROLLBACK. 

-- Start of a transaction (implicit)
DELETE FROM students WHERE student_id = 999;
-- Oops, wrong student!
ROLLBACK;  -- Undoes the DELETE

-- Do it correctly
DELETE FROM students WHERE student_id = 101;
COMMIT;  -- Now it's permanent.

In Oracle SQL*Plus or SQL Developer, auto-commit is usually OFF, so you must commit explicitly. In many application environments, auto-commit might be ON – check your settings.

Section 2.3: Basic Retrieval Queries – SELECT Statement (CLO4 – Applying)

Introduction to SELECT

The SELECT statement retrieves data from one or more tables. It's the DQL (Data Query Language) part of SQL.

Simplest form:

SELECT * FROM table_name;
  • * means "all columns".
  • This returns every row and every column from the table.

Real-life example: You want to see the entire students table: 

SELECT * FROM students;

Select specific columns:

SELECT first_name, last_name, email FROM students;

Only those three columns appear, in that order.

Basic SELECT Syntax Structure 

SELECT column1, column2, ...
FROM table_name
[WHERE condition]
[ORDER BY column [ASC|DESC]];

We'll explore each part step by step.

The WHERE Clause – Filtering Rows

WHERE allows you to retrieve only the rows that match a condition.

Comparison Operators

Operator Meaning Example (in WHERE)
= Equal WHERE major = 'CS'
<> or != Not equal WHERE major <> 'CS'
> Greater than WHERE credits > 3
< Less than WHERE credits < 2
>= Greater than or equal WHERE enrollment_date >= DATE '2025-01-01'
<= Less than or equal WHERE price <= 100

Examples:

-- Find all CS students
SELECT * FROM students WHERE major = 'CS';

-- Find students enrolled after January 1, 2025
SELECT first_name, enrollment_date FROM students WHERE enrollment_date > DATE '2025-01-01';

-- Find courses with more than 3 credits
SELECT title, credits FROM courses WHERE credits > 3;

Logical Operators – AND, OR, NOT

Combine multiple conditions.

Operator Effect
AND All conditions must be true
OR At least one condition true
NOT Reverses the condition

Examples:

-- CS students who enrolled after 2025
SELECT * FROM students 
WHERE major = 'CS' AND enrollment_date > DATE '2025-01-01';

-- CS or EE students
SELECT * FROM students 
WHERE major = 'CS' OR major = 'EE';

-- Students who are NOT in CS
SELECT * FROM students 
WHERE NOT major = 'CS';
-- Same as: WHERE major <> 'CS'

Operator Precedence

NOT > AND > OR
Use parentheses to be clear: 

-- This works but is confusing:
SELECT * FROM students WHERE major = 'CS' OR major = 'EE' AND enrollment_date > DATE '2025-01-01';
-- Better with parentheses:
SELECT * FROM students WHERE (major = 'CS' OR major = 'EE') AND enrollment_date > DATE '2025-01-01';

Special WHERE Operators

BETWEEN – Range checking (inclusive) 

SELECT * FROM products WHERE price BETWEEN 50 AND 100;
-- Equivalent to: price >= 50 AND price <= 100

Example with dates:

SELECT * FROM enrollments WHERE enroll_date BETWEEN DATE '2025-09-01' AND DATE '2025-12-31';

IN – Matches any value in a list 

SELECT * FROM students WHERE major IN ('CS', 'EE', 'ME');
-- Equivalent to: major = 'CS' OR major = 'EE' OR major = 'ME'

Use with numbers:

SELECT * FROM courses WHERE course_id IN (101, 203, 305);

LIKE – Pattern matching with wildcards

Wildcard Meaning Example
% Any number of characters (including zero) 'A%' starts with A; '%son' ends with son; '%a%' contains a
_ Exactly one character '_b%' second character is b; '___' exactly three characters

Examples:

-- Last names starting with 'K'
SELECT * FROM students WHERE last_name LIKE 'K%';

-- Emails from 'university.edu' domain
SELECT * FROM students WHERE email LIKE '%@university.edu';

-- Names with 'a' as the second character (e.g., 'Saba', 'Hassan')
SELECT * FROM students WHERE first_name LIKE '_a%';

-- Names exactly 4 letters long
SELECT * FROM students WHERE first_name LIKE '____';

Important for Oracle:

  • LIKE is case-sensitive by default. Use UPPER(column) to ignore case: 
    SELECT * FROM students WHERE UPPER(last_name) LIKE 'K%';
  • To search for literal % or _, use ESCAPE: 
    SELECT * FROM messages WHERE text LIKE '%50%%' ESCAPE '\';  -- finds "50%"

IS NULL and IS NOT NULL

NULL means "unknown" or "no value". You cannot use = NULL. 

-- Find students who haven't declared a major
SELECT * FROM students WHERE major IS NULL;

-- Find students who have an email address
SELECT * FROM students WHERE email IS NOT NULL;

Sorting Results – ORDER BY

Sorts the output rows.

SELECT first_name, last_name, enrollment_date
FROM students
ORDER BY last_name;   -- ascending (A to Z) by default

Specify direction:

  • ASC – ascending (default)
  • DESC – descending
-- Most recently enrolled students first
SELECT first_name, enrollment_date FROM students ORDER BY enrollment_date DESC;

-- Sort by last name (A-Z), then first name (A-Z) for ties
SELECT * FROM students ORDER BY last_name ASC, first_name ASC;

-- Mix directions: by major (A-Z), then enrollment date (newest first)
SELECT * FROM students ORDER BY major ASC, enrollment_date DESC;

Order by column number (not recommended for readability): 

SELECT first_name, last_name FROM students ORDER BY 2;  -- sorts by last_name (column 2)

Eliminating Duplicates – DISTINCT

Removes duplicate rows from the result.

-- List all majors (each only once)
SELECT DISTINCT major FROM students;

-- Count distinct majors (we'll see COUNT later)
SELECT COUNT(DISTINCT major) FROM students;

Note: DISTINCT applies to all selected columns together: 

SELECT DISTINCT major, enrollment_date FROM students;
-- Means unique pairs of (major, enrollment_date)

Limiting Rows – ROWNUM and FETCH FIRST (Oracle specific)

ROWNUM (Oracle's old way)

ROWNUM assigns a sequential number to each row before sorting. So be careful: 

-- This gives 5 rows, but not necessarily the first 5 alphabetically
SELECT * FROM students WHERE ROWNUM <= 5;

-- To get top 5 by last name, use a subquery:
SELECT * FROM (SELECT * FROM students ORDER BY last_name) WHERE ROWNUM <= 5;

FETCH FIRST (Oracle 12c+ – recommended) 

-- First 5 rows sorted by last name
SELECT * FROM students ORDER BY last_name FETCH FIRST 5 ROWS ONLY;

Section 2.4: Aggregate Functions & Grouping (CLO4 – Applying)

What are Aggregate Functions?

Aggregate functions perform a calculation on a set of rows and return a single value. They are often used with the GROUP BY clause to produce summary reports.

Real-life analogy:
Imagine you have a basket of apples. An aggregate function would tell you:

  • How many apples? (COUNT)
  • Total weight? (SUM)
  • Average weight? (AVG)
  • Heaviest apple? (MAX)
  • Lightest apple? (MIN)

The Five Basic Aggregate Functions

Function Description Example
COUNT(*) Number of rows (including NULLs) COUNT(*)
COUNT(column) Number of non-NULL values in column COUNT(email)
SUM(column) Total of numeric column SUM(price)
AVG(column) Average of numeric column AVG(gpa)
MIN(column) Minimum value MIN(enrollment_date)
MAX(column) Maximum value MAX(credits)

Using Aggregate Functions Without GROUP BY

When you use an aggregate function without GROUP BY, the entire table is treated as one group, and the result is a single row.

Example Table: students

student_id name major gpa
1 Ali CS 3.8
2 Sara CS 3.2
3 Bilal EE 2.9
4 Ayesha CS 3.9
5 Omar EE 3.0

Queries and results:

-- How many students total?
SELECT COUNT(*) FROM students;
-- Result: 5

-- How many students have a GPA? (all do here, but if NULLs existed, they'd be ignored)
SELECT COUNT(gpa) FROM students;
-- Result: 5

-- What is the average GPA?
SELECT AVG(gpa) FROM students;
-- Result: 3.36 (calculated as (3.8+3.2+2.9+3.9+3.0)/5)

-- Highest and lowest GPA
SELECT MIN(gpa), MAX(gpa) FROM students;
-- Result: 2.9 | 3.9

-- Total of all GPAs (not common, but possible)
SELECT SUM(gpa) FROM students;
-- Result: 16.8

You can combine multiple aggregates in one query:

SELECT 
    COUNT(*) AS total_students,
    AVG(gpa) AS avg_gpa,
    MIN(gpa) AS lowest_gpa,
    MAX(gpa) AS highest_gpa
FROM students;

Result:

total_students avg_gpa lowest_gpa highest_gpa
5 3.36 2.9 3.9

Note: AS creates column aliases (temporary names for output).

GROUP BY – Splitting into Groups

GROUP BY divides rows into groups based on unique values in one or more columns. Then aggregate functions are applied to each group separately.

Real-life analogy:
Instead of asking "What is the average GPA of all students?" you ask: "What is the average GPA per major?"
You group students by their major, then compute the average inside each group.

Syntax:

SELECT column1, aggregate_function(column2)
FROM table
GROUP BY column1;

Important rule: Any column in the SELECT that is not an aggregate function must appear in the GROUP BY clause.

Example: Average GPA per major

SELECT major, AVG(gpa) AS avg_gpa
FROM students
GROUP BY major;

Result:

major avg_gpa
CS 3.6333... (average of 3.8, 3.2, 3.9)
EE 2.95 (average of 2.9, 3.0)

Example: Count students per major 

SELECT major, COUNT(*) AS num_students
FROM students
GROUP BY major;

Result:

major num_students
CS 3
EE 2

Multiple columns in GROUP BY

You can group by two or more columns. For example, group by major and enrollment_year: 

SELECT major, enrollment_year, COUNT(*) AS count
FROM students
GROUP BY major, enrollment_year;

This creates a separate group for each unique combination of (major, enrollment_year).

HAVING – Filtering Groups

WHERE filters individual rows before grouping.
HAVING filters groups after grouping (applies to aggregate results).

Real-life analogy:

  • WHERE: "Only look at students with GPA > 3.0" (filters rows before grouping).
  • HAVING: "After grouping, only show majors that have at least 3 students" (filters groups).

Syntax:

SELECT column1, aggregate_function(column2)
FROM table
GROUP BY column1
HAVING condition_on_aggregate;

Example: Show only majors with average GPA greater than 3.0 

SELECT major, AVG(gpa) AS avg_gpa
FROM students
GROUP BY major
HAVING AVG(gpa) > 3.0;

Result: Only CS (3.63) – EE has 2.95, so excluded.

Example: Show only majors with at least 3 students 

SELECT major, COUNT(*) AS student_count
FROM students
GROUP BY major
HAVING COUNT(*) >= 3;

Result: CS (3 students), EE has 2, so excluded.

HAVING without GROUP BY (rare but possible)

If you use HAVING without GROUP BY, the whole table is one group. Example: 

SELECT COUNT(*) FROM students HAVING COUNT(*) > 0;
-- Returns the count only if it's > 0 (always true here)

Order of Execution (Very Important!)

SQL is declarative (you say what you want, not how). But conceptually, the engine processes clauses in this order:

  1. FROM – Identify the table(s).
  2. WHERE – Filter rows (individual rows).
  3. GROUP BY – Group the filtered rows.
  4. HAVING – Filter groups (using aggregate results).
  5. SELECT – Compute expressions and aggregates.
  6. ORDER BY – Sort the final result.

This explains why:

  • You cannot use aggregate functions in WHERE (because grouping hasn't happened yet).
  • You cannot use column aliases in WHERE (because SELECT runs after WHERE).

Example of a full query execution order:

SELECT major, AVG(gpa) AS avg_gpa
FROM students
WHERE gpa > 2.0          -- 1. Filter rows
GROUP BY major           -- 2. Group by major
HAVING AVG(gpa) > 3.0    -- 3. Filter groups
ORDER BY avg_gpa DESC;   -- 4. Sort result

Common Mistakes & Tips

Mistake 1: Forgetting GROUP BY for non-aggregated columns 

-- WRONG:
SELECT major, AVG(gpa) FROM students;
-- Error: 'major' not a GROUP BY expression (Oracle: ORA-00937)

-- CORRECT:
SELECT major, AVG(gpa) FROM students GROUP BY major;

Mistake 2: Using WHERE with aggregate instead of HAVING 

-- WRONG:
SELECT major, AVG(gpa) FROM students WHERE AVG(gpa) > 3.0 GROUP BY major;
-- Error: cannot use aggregate in WHERE

-- CORRECT:
SELECT major, AVG(gpa) FROM students GROUP BY major HAVING AVG(gpa) > 3.0;

Mistake 3: Using column alias in WHERE or HAVING (Oracle specific) 

-- This works in some databases but NOT in Oracle (prior to 23c):
SELECT major, AVG(gpa) AS avg_gpa FROM students GROUP BY major HAVING avg_gpa > 3.0;
-- Oracle error: ORA-00904 (invalid identifier)

-- CORRECT: repeat the aggregate
SELECT major, AVG(gpa) AS avg_gpa FROM students GROUP BY major HAVING AVG(gpa) > 3.0;

Mistake 4: COUNT(*) vs COUNT(column)

  • COUNT(*) includes rows where all columns are NULL (rare, but possible).
  • COUNT(column) ignores NULLs in that column.

Example:

name major
Ali CS
Sara NULL
Bilal CS 
SELECT COUNT(*) FROM students;        -- 3
SELECT COUNT(major) FROM students;    -- 2 (Sara's NULL ignored)

Part A: Joins

What is a Join?

A join combines rows from two or more tables based on a related column. Instead of storing all data in one giant table (which causes redundancy and anomalies), we split data into multiple tables and join them when needed.

Real-life analogy:
You have two lists: one with student names and IDs, another with enrollments (student ID and course). To find "which courses each student is taking," you join the two lists on student ID.

Sample Tables for All Join Examples

Table: students

student_id name major
1 Ali CS
2 Sara CS
3 Bilal EE

Table: enrollments

enrollment_id student_id course_code
101 1 CS101
102 2 CS101
103 2 CS201
104 4 CS101

Notice: student_id = 4 exists in enrollments but not in students (orphan).
student_id = 3 (Bilal) exists in students but has no enrollments.

1. INNER JOIN (or just JOIN)

Returns only rows where there is a match in both tables. 

SELECT students.name, enrollments.course_code
FROM students
INNER JOIN enrollments ON students.student_id = enrollments.student_id;

Result:

name course_code
Ali CS101
Sara CS101
Sara CS201
  • Bilal (no enrollment) excluded.
  • Student 4 (no name) excluded.

INNER JOIN (Venn Diagram)

Oracle syntax alternative (old style, but still works): 

SELECT students.name, enrollments.course_code
FROM students, enrollments
WHERE students.student_id = enrollments.student_id;

2. LEFT OUTER JOIN (or LEFT JOIN)

Returns all rows from the left table, plus matching rows from the right table. If no match, right table columns are NULL. 

SELECT students.name, enrollments.course_code
FROM students
LEFT JOIN enrollments ON students.student_id = enrollments.student_id;

Result:

name course_code
Ali CS101
Sara CS101
Sara CS201
Bilal NULL

Bilal appears with NULL because he has no enrollments.

Real-life use: Find all students, even those not enrolled in any course.

3. RIGHT OUTER JOIN (or RIGHT JOIN)

Returns all rows from the right table, plus matching rows from the left. If no match, left columns are NULL. 

SELECT students.name, enrollments.course_code
FROM students
RIGHT JOIN enrollments ON students.student_id = enrollments.student_id;

Result:

name course_code
Ali CS101
Sara CS101
Sara CS201
NULL CS101

The enrollment with student_id=4 has no matching student, so name is NULL.

Note: RIGHT JOIN is less common; you can usually rewrite it as a LEFT JOIN by swapping table order.

4. FULL OUTER JOIN

Returns all rows from both tables, matching where possible. Missing sides get NULL. 

SELECT students.name, enrollments.course_code
FROM students
FULL OUTER JOIN enrollments ON students.student_id = enrollments.student_id;

Result:

name course_code
Ali CS101
Sara CS101
Sara CS201
Bilal NULL
NULL CS101

5. CROSS JOIN

Cartesian product – every row from first table paired with every row from second table. Rarely used without WHERE. 

SELECT students.name, enrollments.course_code
FROM students
CROSS JOIN enrollments;

If 3 students and 4 enrollments → 12 rows.

Joining a table to itself. Useful for hierarchical data (e.g., employees and managers).

emp_id name manager_id

Part B: Subqueries

A subquery is a query nested inside another SQL query. It can be used in SELECT, FROM, WHERE, HAVING, and even INSERT, UPDATE, DELETE.

Types of Subqueries by Placement

Placement Use
WHERE Filter rows based on subquery result
SELECT Compute a single value per row
FROM Treat subquery as a temporary table (derived table)
HAVING Filter groups based on subquery result

Types by Return Value

Type Returns Allowed operators
Scalar Single value (one row, one column) =, >, <, etc.
Row One row, multiple columns = (with row constructor)
Column One column, multiple rows IN, ANY, ALL, EXISTS
Table Multiple rows, multiple columns Used in FROM

1. Subquery in WHERE with Scalar Result

Find students with GPA above the average GPA.

SELECT name, gpa
FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students);
  • The subquery (SELECT AVG(gpa) FROM students) returns a single number (e.g., 3.2).
  • The outer query compares each student's GPA to that number.

2. IN Operator – Subquery Returns a List

Find students who are enrolled in CS101.

SELECT name
FROM students
WHERE student_id IN (SELECT student_id FROM enrollments WHERE course_code = 'CS101');
  • Subquery returns (1, 2, 4).
  • Outer query picks students with ID in that set.

Equivalent with join:

SELECT DISTINCT students.name
FROM students
JOIN enrollments ON students.student_id = enrollments.student_id
WHERE enrollments.course_code = 'CS101';

When to use subquery vs join?

  • Subquery: when you don't need columns from the second table in the output.
  • Join: when you need columns from both tables.

3. NOT IN – Watch for NULLs!

Find students with no enrollments.

SELECT name
FROM students
WHERE student_id NOT IN (SELECT student_id FROM enrollments);

⚠️ Danger: If the subquery returns any NULL, NOT IN evaluates to UNKNOWN (no rows returned). To be safe: 

SELECT name
FROM students
WHERE student_id NOT IN (SELECT student_id FROM enrollments WHERE student_id IS NOT NULL);

Or use NOT EXISTS (safer for nulls).

4. EXISTS / NOT EXISTS

EXISTS checks whether the subquery returns at least one row. It's often faster for large datasets.

Same query (students with enrollments):

SELECT name
FROM students s
WHERE EXISTS (SELECT 1 FROM enrollments e WHERE e.student_id = s.student_id);

Students with no enrollments:

SELECT name
FROM students s
WHERE NOT EXISTS (SELECT 1 FROM enrollments e WHERE e.student_id = s.student_id);

Why SELECT 1? EXISTS doesn't care about the selected columns; just checks existence.

5. ANY / SOME / ALL

Used with comparison operators.

  • > ANY (...) – greater than at least one value in subquery (same as > MIN).
  • > ALL (...) – greater than all values (same as > MAX).

Find students with GPA higher than any EE student (i.e., higher than the lowest GPA in EE). 

SELECT name, gpa
FROM students
WHERE gpa > ANY (SELECT gpa FROM students WHERE major = 'EE');

Find students with GPA higher than all EE students (higher than the max GPA in EE). 

SELECT name, gpa
FROM students
WHERE gpa > ALL (SELECT gpa FROM students WHERE major = 'EE');

6. Subquery in SELECT (Scalar Subquery)

Show each student's name and the average GPA of their major. 

SELECT name, major, gpa,
       (SELECT AVG(gpa) FROM students s2 WHERE s2.major = s1.major) AS major_avg
FROM students s1;

Correlated subquery: references outer table (s1). Executed once for each outer row.

7. Subquery in FROM (Derived Table / Inline View)

Find the average GPA per major, then show majors where avg GPA > 3.0. 

SELECT major, avg_gpa
FROM (SELECT major, AVG(gpa) AS avg_gpa FROM students GROUP BY major)
WHERE avg_gpa > 3.0;

The subquery creates a temporary table that the outer query uses.

8. Subquery in HAVING

Find majors where the average GPA is higher than the overall average GPA. 

SELECT major, AVG(gpa)
FROM students
GROUP BY major
HAVING AVG(gpa) > (SELECT AVG(gpa) FROM students);

Correlated vs Non‑Correlated Subqueries

Type Description Executed Example
Non‑correlated Independent of outer query Once WHERE gpa > (SELECT AVG(gpa) FROM students)
Correlated References outer query Once per outer row WHERE EXISTS (SELECT 1 FROM enrollments e WHERE e.student_id = s.student_id)

Practical Example – Combining Join and Subquery

Problem: List students who are enrolled in more than one course.

Solution with join + GROUP BY:

SELECT s.name, COUNT(e.course_code) AS num_courses
FROM students s
JOIN enrollments e ON s.student_id = e.student_id
GROUP BY s.student_id, s.name
HAVING COUNT(e.course_code) > 1;

Solution with subquery in WHERE:

SELECT name
FROM students
WHERE student_id IN (
    SELECT student_id
    FROM enrollments
    GROUP BY student_id
    HAVING COUNT(*) > 1
);

Before building a database, you must understand what data to store and how data items relate. A data model is a blueprint. The most common is the Entity-Relationship (ER) model.

3.2 Extended Entity-Relationship (EER) Model

EER adds supertype/subtype (inheritance) and constraints.

Supertype / Subtype

  • Supertype – general entity (e.g., Person).
  • Subtype – specialized entity (e.g., Student, Professor).
  • Subtype inherits all attributes of supertype, plus its own.
  • Relationship: Person IS-A Student (specialization).

Real-life example: In a university, a Person can be a Student, Faculty, or Staff. Each subtype has unique attributes (Student: Major, GPA; Faculty: Rank, Office).

3.3 Mapping ER/EER to Relational Model (Overview)

We will cover this in detail in a later section, but here's the gist:

  1. Each regular entity → a table (attributes become columns, PK remains PK).
  2. Weak entity → table with foreign key referencing owner and partial key as PK.
  3. 1:1 relationship – can be merged into one table or two tables with foreign key on either side.
  4. 1:N relationship – add foreign key in the "many" side table referencing the "one" side.
  5. M:N relationship → create a new associative table containing both foreign keys (composite PK).
  6. Multivalued attribute → separate table (one column for the attribute, plus foreign key to entity).
  7. Supertype/Subtype – options:
    • One table for supertype, separate tables for subtypes (foreign key to supertype).
    • Single table with type discriminator (all attributes, many NULLs).
    • Only subtypes (if supertype is abstract).

Section 4: Relational Data Model & Mapping (CLO2 – Creating)

4.1 Relational Data Model Concepts

What is the Relational Model?

Proposed by Edgar F. Codd in 1970. Data is organized into relations (tables). Each relation has:

  • Tuples (rows) – each row is a record.
  • Attributes (columns) – each column has a name and a data type.

Real-life analogy: An Excel spreadsheet – rows are records, columns are fields. But relational model is more formal and powerful.

Key Properties of a Relation

  1. Each cell contains exactly one value (atomic) – no repeating groups or arrays.
  2. All rows are distinct (no duplicates) – but SQL allows duplicates unless you use DISTINCT.
  3. Order of rows and columns is irrelevant (but in practice, we order for readability).
  4. Each column has a unique name within the table.

Relational Schema vs Instance

  • Schema – the structure (table name, column names, data types, constraints). Changes rarely.
  • Instance – the actual data (rows). Changes frequently.

Example:

Schema: Student(student_id: INTEGER, name: VARCHAR(50), major: CHAR(2))
Instance: (101, 'Ali', 'CS'), (102, 'Sara', 'EE')

Keys in the Relational Model

Key Type Definition Example
Superkey Any set of attributes that uniquely identifies a row (may contain extra attributes) {student_id}, {student_id, name}
Candidate Key Minimal superkey (no extra attributes) {student_id}, {email}
Primary Key (PK) One candidate key chosen by the designer {student_id}
Alternate Key Candidate keys not chosen as PK {email}
Foreign Key (FK) Attribute(s) that reference the PK of another table (or same table) In Enrollment table, student_id references Student(student_id)
Composite Key A key consisting of two or more attributes {student_id, course_id} in Enrollment

Relational Integrity Constraints

Constraint Description Example
Domain Constraint Each attribute value must be from its domain (data type, range) gpa between 0 and 4
Entity Integrity Primary key cannot be NULL student_id must have a value
Referential Integrity Foreign key value must either match a PK in referenced table or be NULL (if allowed) Every student_id in Enrollment must exist in Student
Key Uniqueness No duplicate PK or candidate key values Two students cannot have same student_id

In pure relational model, there are no duplicate rows. In SQL, SELECT * can return duplicates, but you can add DISTINCT. Also, SQL tables are multisets (bags) by default.

4.2 Mapping ER/EER to Relational Schema

We now convert an ER diagram into a set of tables (relations) that can be implemented in Oracle.

Step-by-Step Mapping Rules

Rule 1: Map Regular (Strong) Entities

Create a table with all simple attributes of the entity. Choose the identifier (PK) as the table's PK. Composite attributes are broken into their components.

Example ER:
Entity Student with attributes: student_id (PK), first_name, last_name, birthdate, phone (multivalued).

Relational Schema:

Student(student_id, first_name, last_name, birthdate)

Multivalued attribute phone is mapped separately (Rule 7).

Rule 2: Map Weak Entities

Create a table for the weak entity. Include the PK of the owner (strong) entity as a foreign key. The PK of the weak entity is the combination of that foreign key + its partial key.

Example: Weak entity Room owned by Hotel. Partial key: room_number. Owner PK: hotel_id.

Tables:

Hotel(hotel_id, name)
Room(hotel_id, room_number, capacity)
PK: (hotel_id, room_number)
FK: hotel_id references Hotel(hotel_id)

Rule 3: Map 1:1 Relationships

Three options. Choose based on participation.

Option A (merge into one table) – if both participations are total (rare).

Option B (foreign key in one table) – add PK of one side as FK in the other. Choose the side where participation is total, or whichever reduces NULLs.

Option C (separate table) – create a new table with both PKs as FKs. Usually not needed.

Example: Employee has Office (1:1, each employee has one office, each office belongs to one employee). Put office_id as FK in Employee. 

Employee(emp_id, name, office_id)
Office(office_id, location)
FK: office_id references Office(office_id)

Rule 4: Map 1:N Relationships

Add the PK of the "1" side (parent) as a foreign key in the table of the "N" side (child). Do not create a separate table.

Example: Department has many Employees (1:N). Each employee belongs to one department. 

Department(dept_id, name)
Employee(emp_id, name, dept_id)
FK: dept_id references Department(dept_id)

Rule 5: Map M:N Relationships

Create a new associative (bridge) table that contains the PKs of both entities as foreign keys. The combination becomes the composite PK. Any attributes of the relationship are added to this table.

Example: Student enrolls in Course (M:N). Relationship has attribute grade. 

Student(student_id, name)
Course(course_id, title)
Enrollment(student_id, course_id, grade)
PK: (student_id, course_id)
FK: student_id references Student(student_id)
FK: course_id references Course(course_id)

Rule 6: Map Multivalued Attributes

Create a separate table. The table contains:

  • The multivalued attribute itself.
  • The PK of the original entity as a foreign key (to link back).

Example: Student has phone (multivalued). 

Student(student_id, name)   -- no phone here
Student_Phone(student_id, phone)
PK: (student_id, phone)
FK: student_id references Student(student_id)

Rule 7: Map Composite Attributes

Flatten them into their component attributes. Do not create a separate table.

Example: Employee has address composed of street, city, zip. 

Employee(emp_id, name, street, city, zip)

Rule 8: Map Derived Attributes

Do not store them in the database. Compute them on the fly (e.g., in queries or views). But if you must store (for performance), you can, but you'll need to update it manually.

Example: age derived from birthdate. In SQL, compute with FLOOR(MONTHS_BETWEEN(SYSDATE, birthdate)/12).

Rule 9: Map Specialization (Supertype/Subtype) – EER

Three common strategies:

Option A (Multiple tables – one per subclass, no supertype table): Use only if supertype has few attributes and is not needed without subclass. Not common.

Option B (One table with type discriminator): All attributes of supertype and all subtypes in one table. Many NULLs. Simple, good when subtypes have few unique attributes.

Option C (Supertype table + separate subtype tables): Best for most cases. Supertype table holds common attributes. Each subtype table has its unique attributes plus FK to supertype PK.

Example: Person supertype, Student and Professor subtypes. Person has (PID, name). Student has (Major, GPA). Professor has (Rank, Office).

Tables (Option C):

Person(PID, name)  -- PK: PID
Student(PID, Major, GPA)  -- PK: PID, FK references Person(PID)
Professor(PID, Rank, Office) -- PK: PID, FK references Person(PID)

Constraints: For disjoint specialization, ensure a PID appears in at most one subtype. For total specialization, ensure every Person appears in a subtype (can be enforced by triggers or application logic).

Section 5: Functional Dependencies & Normalization (CLO3 – Analyzing)

Why Normalization?

When we design a database, we might create bad schemas that cause problems. Normalization is the process of removing redundancy and avoiding anomalies.

The Three Anomalies (What Can Go Wrong)

Consider this StudentCourse table (not normalized):

student_id name major course_id course_title grade
101 Ali CS CS101 Programming A
101 Ali CS CS201 Databases B
102 Sara EE EE101 Circuits A

1. Insertion Anomaly – Cannot add a new course with no students enrolled (would need NULL for student info).

2. Deletion Anomaly – If Ali drops both courses, we lose his name and major entirely.

3. Update Anomaly – If Ali changes his major, we must update multiple rows; if we miss one, data becomes inconsistent.

Goal of Normalization: Break one big table into smaller, well-structured tables to eliminate these anomalies.

5.1 Functional Dependencies (FDs)

Definition

A functional dependency (FD) is a constraint between two sets of attributes in a relation.

Notation: X → Y (read: "X functionally determines Y" or "Y is functionally dependent on X")

Meaning: For any two rows in the table, if they have the same value for all attributes in X, they must also have the same value for all attributes in Y.

Real-life example: In a Student table, student_id → name, major. If two rows have the same student_id, they must have the same name and major. That makes sense because student_id is a key.

Trivial vs Non-Trivial FDs

  • Trivial FD: X → Y where Y ⊆ X (e.g., student_id, name → student_id). Always true.
  • Non-Trivial FD: Y is not a subset of X (e.g., student_id → name).

Properties of FDs (Armstrong's Axioms)

Given FDs, we can derive new FDs using:

  1. Reflexivity: If Y ⊆ X, then X → Y (trivial)
  2. Augmentation: If X → Y, then XZ → YZ for any Z
  3. Transitivity: If X → Y and Y → Z, then X → Z

Derived rules:

  • Union: If X → Y and X → Z, then X → YZ
  • Decomposition: If X → YZ, then X → Y and X → Z
  • Pseudotransitivity: If X → Y and WY → Z, then WX → Z

Closure of a Set of Attributes

The closure X⁺ is the set of all attributes that can be functionally determined by X using given FDs.

Algorithm to compute closure:

closure = X
repeat
    for each FD (L → R) in F:
        if L ⊆ closure then closure = closure ∪ R
until no change

Example: Given R(A, B, C, D) with FDs: A → B, B → C, BD → D (trivial). Compute A⁺.

Start: closure = {A}

  • A → B: A in closure → add B → {A, B}
  • B → C: B in closure → add C → {A, B, C}
  • BD → D: D not in closure yet, but BD? B is in closure, D not, so cannot apply.
    Result: A⁺ = {A, B, C}

Why closure matters: To check if X is a candidate key, compute X⁺. If X⁺ contains all attributes of the relation, then X is a superkey. Minimal such X is a candidate key.

5.2 Normal Forms (1NF, 2NF, 3NF, BCNF)

First Normal Form (1NF)

Rule: All attribute values must be atomic (no repeating groups or composite values). Every row/column intersection contains exactly one value.

Violation example: A student table with a phone_numbers column containing "123456, 789012".

Fix: Create a separate table for student_phone (multivalued attribute mapping, as we did in Section 4).

After 1NF, our table is a proper relational table.

Second Normal Form (2NF)

Rule: The table must be in 1NF and have no partial dependencies. A partial dependency occurs when a non-key attribute depends on only part of a composite candidate key.

Example violation: Enrollment(student_id, course_id, student_name, grade)

  • Candidate key: (student_id, course_id)
  • student_name → student_id (non-key depends on part of key). This is a partial dependency.

Fix: Decompose into:

Student(student_id, student_name)
Enrollment(student_id, course_id, grade)

Third Normal Form (3NF)

Rule: The table must be in 2NF and have no transitive dependencies. A transitive dependency occurs when a non-key attribute depends on another non-key attribute (rather than directly on the key).

Example violation: Employee(emp_id, emp_name, dept_id, dept_location)

  • Key: emp_id
  • dept_id → dept_location (non-key determines another non-key)
  • emp_id → dept_id → dept_location, so transitive dependency.

Fix: Decompose into:

Employee(emp_id, emp_name, dept_id)
Department(dept_id, dept_location)

Boyce-Codd Normal Form (BCNF)

Rule: A stronger version of 3NF. For every non-trivial FD X → Y, X must be a superkey.

Any BCNF table is automatically in 3NF, but not vice versa.

Example violation (3NF but not BCNF):
CourseInstructor(course_id, instructor_id, room)
FDs:

  • course_id → instructor_id (each course has one instructor – but wait, this would make instructor_id functionally dependent on course_id. Actually, let's use classic example:)

Classic BCNF violation:
StudentCourseInstructor(student_id, course_id, instructor_id)
Suppose each instructor teaches only one course, and each course has one instructor, but a student can take multiple courses.
FDs: instructor_id → course_id (instructor determines course). But candidate key is (student_id, course_id) – instructor_id is not a superkey.

Fix: Decompose into:

CourseInstructor(course_id, instructor_id)  -- but actually instructor_id determines course_id, so better:
Instructor(instructor_id, course_id)
Enrollment(student_id, course_id)

In practice: 3NF is usually sufficient. BCNF is used when 3NF still has redundancy from overlapping candidate keys.

5.4 Real-World Normalization Example

Unnormalized table: Order(order_id, customer_name, customer_city, order_date, product_id, product_name, quantity)

Assume FDs:

  • order_id → customer_name, customer_city, order_date
  • product_id → product_name
  • (order_id, product_id) → quantity

Step 1 – 1NF: Already atomic.

Step 2 – Find candidate keys: (order_id, product_id) is the composite key.

Step 3 – 2NF: Partial dependencies:

  • order_id → customer_name, customer_city, order_date (depends on part of key). Remove.
  • product_id → product_name (depends on part of key). Remove.

Decompose into:

Order(order_id, customer_name, customer_city, order_date)  -- PK: order_id
Product(product_id, product_name)  -- PK: product_id
OrderLine(order_id, product_id, quantity)  -- PK: (order_id, product_id)

Step 4 – 3NF: Check transitive dependencies in Order:
order_id → customer_name, customer_city? No transitive, fine.
Order is in 3NF (all non-keys depend directly on the key).
Product is in 3NF.
OrderLine is in 3NF.

Final normalized schema: no anomalies.

Quick Tips for Exams

  1. Find candidate keys first – usually by computing closures.
  2. Identify FDs from business rules (not just given ones).
  3. Partial dependency = non-key depends on part of composite key.
  4. Transitive dependency = non-key depends on another non-key.
  5. Decomposition must be lossless (able to join back) and dependency preserving (all FDs can be enforced separately). For exams, focus on lossless decomposition using common sense.

20-Mark Normalization Exam Question – Solved Example

Question:
Consider the following relation schema for a library loan system:

BorrowRecord (member_id, member_name, member_address, book_id, book_title, author, loan_date, return_date, days_borrowed)

Assumptions (Functional Dependencies):

  1. member_id → member_name, member_address
  2. book_id → book_title, author
  3. member_id, book_id, loan_date → return_date, days_borrowed

(Note: days_borrowed is always equal to return_date - loan_date, so it is derivable, but treat it as given for this exercise.)

Tasks (20 marks):

  • (a) Identify the candidate key(s) for the relation. (2 marks)
  • (b) In which normal form is the relation? Justify. (4 marks)
  • (c) Decompose the relation into 3NF (or BCNF if possible). Show each step of decomposition with reasoning. (10 marks)
  • (d) Verify that your decomposition is lossless and preserves dependencies. (4 marks)

Solution

(a) Candidate Key (2 marks)

We need to find the minimal set of attributes that can determine all others.

Given FDs:

  • (1) member_id → member_name, member_address
  • (2) book_id → book_title, author
  • (3) member_id, book_id, loan_date → return_date, days_borrowed

Start with {member_id, book_id, loan_date} (call this set X).

Compute closure X⁺:

  • Start: X = {member_id, book_id, loan_date}
  • Using (1): member_id → member_name, member_address → add them.
  • Using (2): book_id → book_title, author → add them.
  • Using (3): X itself → return_date, days_borrowed → add them.

Now X⁺ contains: member_id, book_id, loan_date, member_name, member_address, book_title, author, return_date, days_borrowed → all attributes of the relation.

So {member_id, book_id, loan_date} is a superkey.

Is it minimal? Cannot remove member_id (would lose determination of member_name and member_address). Cannot remove book_id (would lose book_title, author). Cannot remove loan_date (the FD (3) needs it to determine return_date and days_borrowed). So it is the only candidate key.

Answer: (member_id, book_id, loan_date) is the candidate key.

(b) Current Normal Form (4 marks)

Check 1NF: All values are atomic → satisfied.

Check 2NF: A relation is in 2NF if it is in 1NF and no partial dependency exists.
A partial dependency occurs when a non‑prime attribute (not part of any candidate key) depends on only part of a composite candidate key.

Here candidate key = (member_id, book_id, loan_date).

  • member_id is part of the key.
  • book_id is part of the key.
  • loan_date is part of the key.

Non‑prime attributes: member_name, member_address, book_title, author, return_date, days_borrowed.

Now examine FDs:

  • member_id → member_name, member_address.
    Here member_id is a proper subset of the key, and it determines non‑prime attributes. → Partial dependency exists.

Therefore the relation is not in 2NF.

Answer: The relation is in 1NF only (because it has partial dependencies).

(c) Decompose to 3NF (or BCNF) (10 marks)

We need to remove partial dependencies first (achieve 2NF), then remove transitive dependencies (achieve 3NF).

Step 1 – Remove partial dependencies using the violating FDs.

Violating FD (1): member_id → member_name, member_address

Create a new table R1 with these attributes:

R1 (member_id, member_name, member_address)

Primary key: member_id

Remove member_name and member_address from the original relation. The original now becomes: 

R_remaining (member_id, book_id, loan_date, book_title, author, return_date, days_borrowed)

Violating FD (2): book_id → book_title, author

Create new table R2:

R2 (book_id, book_title, author)

Primary key: book_id

Remove book_title and author from R_remaining. Now R_remaining becomes: 

R3 (member_id, book_id, loan_date, return_date, days_borrowed)

Now check candidate key for R3: From the original FD (3): member_id, book_id, loan_date → return_date, days_borrowed. No partial dependencies remain because the key is composite and all non‑key attributes (return_date, days_borrowed) depend on the whole key. So R3 is in 2NF (and also in 3NF because there is no transitive dependency – the only non‑prime attributes depend directly on the key).

Step 2 – Check for transitive dependencies (for 3NF).

  • In R1: member_id → member_name, member_address (no transitive – fine).
  • In R2: book_id → book_title, author (fine).
  • In R3: Candidate key (member_id, book_id, loan_date). Is there any FD like X → Y where X is not a superkey and Y is non‑prime? No. So R3 is already in 3NF (and also in BCNF because all determinants are superkeys – in R3 the only determinant is the candidate key itself).

Thus the final decomposition into 3NF is:

R1 (member_id, member_name, member_address)
R2 (book_id, book_title, author)
R3 (member_id, book_id, loan_date, return_date, days_borrowed)

(d) Verify Lossless Join & Dependency Preservation (4 marks)

Lossless join: We can check using the chase test or simple observation:
The common attribute between R1 and R3 is member_id, and member_id is a candidate key of R1. Similarly, book_id is common between R2 and R3 and is a candidate key of R2. For a binary decomposition to be lossless, the intersection must be a superkey in at least one of the two tables. Here all decompositions satisfy that. Hence the overall decomposition is lossless.

Dependency preservation: The original FDs are:

  • FD1: member_id → member_name, member_address → preserved in R1.
  • FD2: book_id → book_title, author → preserved in R2.
  • FD3: member_id, book_id, loan_date → return_date, days_borrowed → preserved in R3.

All FDs are preserved without joining tables. Thus dependency preservation holds.

Total marks earned in this example: 20/20
